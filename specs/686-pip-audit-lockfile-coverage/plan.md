# Plan: pip-audit lockfile coverage — audit the full hash-locked dependency graphs

- Spec: specs/686-pip-audit-lockfile-coverage/spec.md

## Architecture
One workflow job plus additive tests; no new workflow, job or application module. `.github/workflows/security.yml` changes inside the existing `dependency-audit` job only. The `Install pip-audit` step is pinned to `pip install pip-audit==2.10.1`. The two pre-existing audits of the direct manifests (`pip-audit -r deploy/worker/ubuntu/requirements-runtime.txt` and `pip-audit -r api/requirements-api.txt`) stay byte-identical. After them, two new steps audit the full hash-locked graphs with `--disable-pip`, JSON output and an explicit report path: `pip-audit --disable-pip -r api/requirements-api.lock.txt --format json --output pip-audit-api-lock.json` and the worker equivalent. A single upload step with `if: always()` publishes both JSON reports as `pip-audit-reports-${{ github.sha }}` through the existing SHA-pinned `actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02` at 14-day retention. A negative self-test writes `requests==2.20.0` to a temp file and runs the same `pip-audit --disable-pip` command inside an explicit guard that fails the step when the audit unexpectedly succeeds. `secret-scan`, `security-result`, the workflow triggers, permissions, concurrency, timeouts and every action pin are untouched. `tests/quality/test_security_merge_gate.py` gains five additive cases that parse the workflow YAML and assert the exact pin, both verbatim lockfile commands, the artifact upload with both report filenames, the negative self-test shape, and a premise that each lockfile carries a substantial transitive-only pin set.

## Decisions
- Audit the lockfiles at all, rather than only pinning the tool: pinning pip-audit fixes reproducibility but leaves the 16 API and 50 worker transitive pins unaudited; the lockfiles describe what production installs, so auditing them is the actual coverage fix the issue asks for.
- Keep the direct-manifest audits byte-identical and add the lockfile audits after them: the existing commands are already tested by pre-#686 assertions and removing them would trade one coverage set for another; additive steps give full-graph coverage without changing the established gate.
- `--disable-pip` on both lockfile audits and on the self-test: it audits the hash-locked graph without building a temporary virtualenv in the constrained runner, and reusing it in the self-test means the proof exercises the shipped command shape.
- `--format json --output <report>` rather than console output: a JSON report is machine-readable provenance of the exact resolved versions, and writing it to a file lets the artifact upload carry the evidence even when the audit exits non-zero.
- Artifact upload with `if: always()`: a failed audit is exactly the case where the report is needed, so the upload must not depend on audit success; 14-day retention matches the existing gitleaks artifact.
- Reuse the existing SHA-pinned `upload-artifact` action: the repository already pins that exact commit; adding a second pin or bumping it would widen the diff for no gain.
- Negative self-test with `requests==2.20.0`: the pin has published CVEs (CVE-2018-18074, CVE-2023-32681), so a working gate must exit non-zero; the step's guard turns an unexpectedly clean audit into a hard failure, which is the only way to prove the gate is not a no-op rather than asserting it in prose.
- No `continue-on-error` and no step-level `if` on the self-test: either would let the failing audit be swallowed, which is the failure mode the test rejects by construction.
- Assert through parsed YAML with verbatim constants: the test pins the production bytes (exact command lines, exact report filenames, exact pin) so command or pin drift fails the suite instead of silently reducing coverage; the negative self-test is checked structurally because its shell body needs a guard, not an exact string.
- Test the premise separately: a transitive-only pin-set check (`test_lockfiles_cover_transitive_only_pins`) proves the new audits add coverage rather than duplicate the direct ones, with thresholds that leave lock-regeneration headroom.
- Change Contract declaration is load-bearing: the diff is under `.github/workflows/**`, so the autonomous policy derives `Production impact: CONTROL_PLANE`. The PR Change Contract must declare `Production impact: CONTROL_PLANE`, `VPS deployment: NOT REQUIRED`, `Ubuntu worker/relay update: NOT REQUIRED`, `Production safety envelope: NOT REQUIRED`, `VPS execution capability: NOT APPLICABLE`, `Ubuntu worker execution capability: NOT APPLICABLE` and `Operator actions expected: 0`; a VPS-REQUIRED or contradicting contract would be rejected.

## Runtime feedback
- The gap was invisible by construction: the gate audited the declared manifests, which list 7 pins each, while production installs the 23-pin and 57-pin lockfile graphs; 16 and 50 pins respectively were never scanned, so a vulnerable transitive dependency could ship with a green pipeline.
- Blast radius is merge-time only: the change is a required pre-merge Security gate, not a runtime component; a bug in it blocks merges rather than affecting serving traffic, which is why the negative self-test matters more than a runtime probe here.
- Implementation feedback: `--disable-pip` avoids temp-venv creation in the constrained runner and the self-test reuses it deliberately so the proof matches the shipped command; the upload must be `if: always()` because the report is most valuable when the audit fails.
- Emergent fix: the self-test step name originally carried an unquoted colon and broke YAML parsing; it is quoted now and the workflow parses. This is recorded because a YAML parse failure would have broken the whole Security workflow, not just the new step.
- Test-harness feedback: the five cases are additive and parse the real workflow YAML; the premise case is GREEN on both sides by design because it describes the lockfile shape, while the four workflow cases flip from RED to GREEN with the change.
