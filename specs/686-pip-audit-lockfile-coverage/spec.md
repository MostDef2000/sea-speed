# Spec: pip-audit lockfile coverage — audit the full hash-locked dependency graphs

- Issue: #686

## Product outcome
Issue #686 closes a verification coverage gap in the Security gates workflow. The `dependency-audit` job in `.github/workflows/security.yml` audited only the two direct requirement manifests — `api/requirements-api.txt` (7 pins) and `deploy/worker/ubuntu/requirements-runtime.txt` (7 pins) — and never the full hash-locked graphs those manifests resolve to: `api/requirements-api.lock.txt` (23 pins) and `deploy/worker/ubuntu/requirements-runtime.lock.txt` (57 pins). That left 16 API pins and 50 worker pins, all transitive dependencies actually installed in production, unaudited by any automated gate. The gap was a coverage defect, not a found CVE: the pipeline could stay green while a vulnerable transitive pin shipped. The change installs `pip-audit==2.10.1` at an exact version, keeps the two existing direct-manifest audits byte-identical, adds a `--disable-pip` JSON audit of each full lockfile, uploads both JSON reports as a SHA-pinned 14-day artifact so the resolved graph and versions are visible in CI, and adds a negative self-test that feeds the known-vulnerable pin `requests==2.20.0` through the same audit command and fails the step if the audit unexpectedly reports it clean, proving the gate is not a no-op. No production runtime, deploy script, worker or application source changes.

## User scenarios
- A maintainer opens a PR that bumps a transitive pin in `api/requirements-api.lock.txt`: the `dependency-audit` job runs the full-lockfile audit, and a vulnerability in that transitive pin turns the job red and therefore fails the required Security gate, even though the direct manifest lists only the top-level requirements.
- A maintainer opens a PR that bumps a transitive pin in `deploy/worker/ubuntu/requirements-runtime.lock.txt`: the worker full-lockfile audit covers the 50 transitive-only pins; a vulnerable one fails the gate.
- A maintainer inspects a finished `dependency-audit` run: the `pip-audit-reports-<sha>` artifact contains `pip-audit-api-lock.json` and `pip-audit-worker-lock.json` listing every resolved package version and its findings, so the exact audited graph is retrievable from CI rather than inferred from the manifests.
- A maintainer checks that the gate is not vacuous: the negative self-test step audits `requests==2.20.0`, a pin with published CVEs, and the step fails unless pip-audit exits non-zero on it, so an audit that silently reports everything clean breaks the workflow instead of passing it.
- A maintainer reads the workflow: the two original direct-manifest audit commands, the gitleaks job, the `security-result` aggregation and every action pin are unchanged, and the new steps are additive inside `dependency-audit` only.

## Requirements
1. Exact pip-audit pin: the `Install pip-audit` step becomes `pip install pip-audit==2.10.1`; no bare unpinned `pip install pip-audit` remains, so the audit tool cannot drift under the gate.
2. Existing audits preserved: `pip-audit -r deploy/worker/ubuntu/requirements-runtime.txt` and `pip-audit -r api/requirements-api.txt` stay byte-identical inside `dependency-audit`; the new lockfile audits are in addition to, never a replacement for, the direct-manifest audits.
3. Full API lockfile audit: add `pip-audit --disable-pip -r api/requirements-api.lock.txt --format json --output pip-audit-api-lock.json`.
4. Full worker lockfile audit: add `pip-audit --disable-pip -r deploy/worker/ubuntu/requirements-runtime.lock.txt --format json --output pip-audit-worker-lock.json`.
5. `--disable-pip` on both lockfile audits: the flag avoids creating a temporary virtualenv inside the constrained runner while auditing the hash-locked graph directly; the same mode is used by the negative self-test so it exercises the shipped command shape.
6. Report provenance: a step with `if: always()` uploads `pip-audit-api-lock.json` and `pip-audit-worker-lock.json` as `pip-audit-reports-${{ github.sha }}` using the existing SHA-pinned `actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02` and 14-day retention, so reports survive even when an audit finds a vulnerability and fails the job.
7. Negative self-test: a step writes `requests==2.20.0` (CVE-2018-18074, CVE-2023-32681) to a temp file and runs the same `pip-audit --disable-pip` command under an explicit guard that exits non-zero if the audit unexpectedly succeeds; the step has no `continue-on-error` and no step-level `if`, so an unexpectedly clean audit is a hard failure that proves the gate can detect a known-vulnerable pin.
8. Bounded surface: no other workflow job or setting changes — `secret-scan`, `security-result`, the `on:` events, `permissions`, `concurrency`, timeouts and all action pins stay as they are; no source, deploy, worker or application file changes; the only test change is additive coverage in `tests/quality/test_security_merge_gate.py`.
9. Testability: the workflow is asserted through parsed YAML with verbatim command constants (exact pin, both lockfile commands, both report filenames, the negative self-test shape), plus a premise test proving each lockfile carries a substantial transitive-only pin set so the new audits add real coverage rather than duplicate the direct ones.

## Runtime feedback
- Coverage-gap class (issue #686): the gate scanned the declared top-level requirements but not the hash-locked graphs the deployment actually installs, so 16 API and 50 worker transitive pins were invisible to it. This was a verification coverage defect, not a detected CVE; the value of the change is that a vulnerable transitive pin now fails a required gate.
- Implementation feedback: `--disable-pip` is load-bearing in the constrained runner — it audits the hash-locked graph without building a temporary virtualenv — and the negative self-test reuses exactly that mode, so the proof exercises the shipped command shape rather than a different one. The upload must be `if: always()`: a failed audit is precisely when the JSON report matters, so the report cannot be gated on audit success.
- Emergent fix during implementation: the negative self-test step name originally contained an unquoted colon, which broke YAML parsing of the workflow. It is now quoted (`"Negative self-test: known-vulnerable pin must fail the audit"`), and the workflow parses cleanly; no other step name or command changed.
- Test-harness feedback: the five new cases are additive to `tests/quality/test_security_merge_gate.py` and assert the production workflow bytes through parsed YAML rather than re-implementing the gate. RED before the fix: 5 failed / 9 passed (the pin, both lockfile commands, the artifact upload and the self-test absent on the base). GREEN after: 11 passed plus 80 subtests. The transitive-coverage premise case is GREEN on both sides by design — `requests==2.20.0` is not the point there, the 16/50 transitive-only pin sets are.
- Verification feedback: the full battery is 1444 tests OK (skipped=2); repository, contracts, quality, workflow and token validators PASS; ruff PASS. The change is CI control-plane only, so no runtime probe applies.
