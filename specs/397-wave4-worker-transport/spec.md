# Spec: wave-4 worker transport — requests transport/posting extraction (move-only)

- Issue: #397
- Specification: specs/397-wave4-worker-transport/spec.md

## Product outcome

Waves 1-3 extracted the pure kernel (#475), the media/reader layer (#476) and the cv2 render/snapshot layer (#479); the worker still mixes the requests transport/posting layer with analytics/crossing/speed domain state and the supervision main loop. Wave 4 extracts the transport layer verbatim into NEW `worker/worker_transport.py` (6 defs: `fetch_remote_roi`, `post_state`, `post_event`, `post_passage`, `fetch_speed_lines_config`, `fetch_crossing_line_config` — AST-identical bodies verified against HEAD before and after the cut) plus the three TTL caches that move WITH their fetchers (`_roi_cache`, `_speed_lines_cache`, `_crossing_line_cache`) — the first wave that moves module-level STATE, under an object-identity contract. The compatibility gate's `MODULE_SOURCES` extends to the four-file union (worker + worker_media + worker_render + worker_transport; semantics unchanged, fail-closed preserved).

The full order cut was re-derived from live source and the cache read/write graph was mapped programmatically before the first write. The moved caches satisfy the identity-contract preconditions: the ONLY Store access to each moved cache name in the whole worker+transport source is its defining dict literal (verified by AST walk — zero rebindings anywhere); every other access is an in-place mutation (item assignment / dict.update / .get). Because the worker re-exports the cache OBJECTS via ImportFrom, `worker._crossing_line_cache` IS `worker_transport._crossing_line_cache` — staying readers (crossing_overlay_summary reads `_crossing_line_cache`) observe mover mutations and vice versa. That is the safety argument for moving state, documented in this trio and pinned by an identity test.

Deliberate STAYS (recorded, not silently dropped):
- `fetch_speed_config` + `_speed_config_cache` — the fetcher is NOT in the work-order cut list (only its cache was listed for the decision); the cache stays with its staying fetcher (all 9 accesses inside `fetch_speed_config`).
- `post_crossing`, `flush_crossing_posts`, `_post_live_envelope_sync`, `_ensure_live_publisher`, `post_live_envelope` — posting-family members not listed in the cut (crossing/live-publisher flow, entangled with staying domain state and the publisher loop); a later wave can move them with their caches.
- `_crossing_counts`, `_crossings_by_class` — crossing-DOMAIN state with staying mutators (`update_crossing_counts`, `reset_crossing_counts`) and staying readers; `fetch_crossing_line_config` (the mover) does not touch them.
- `_roi_processing_points` — the ONLY rebinding global in the file (`global` + assignment inside staying `prepare_roi_processing_frame`, read by staying `detection_inside_road_roi`); `fetch_remote_roi` does not reference it, so it stays in the worker untouched.
- `_crossing_track_sides`, `_crossing_pending_posts`, `_crossing_vlz_date`, `_line_speed_state`, `_roi_processing_points` — staying domain-state mutables untouched by any mover.

No REQUIRED_ENV_NAMES call site is LOST: `post_state`/`post_event`/`post_passage` move the `SEA_SPEED_API_URL`/`SEA_SPEED_API_TOKEN` reads INTO worker_transport, and the gate scans the four-file union — the required-env set is still fully covered (verified by grep + gate CLI + unit test). `HLS_URL` (worker_media) and `MODEL_NAME` (worker) were never in the movers.

## User scenarios

- US-1: the runtime worker boots on the Ubuntu worker host → `import worker_transport` resolves as a flat sibling (shipped by the exact artifacts and the installer) → `main()`'s `post_state`/`post_event`/`post_passage` call sites and the staying callers (`road_roi_enabled`/`parse_road_roi_polygon`/`prepare_roi_processing_frame` → `fetch_remote_roi`; `update_crossing_counts` → `fetch_crossing_line_config`; `update_speed_lines_estimate`/`draw_speed_lines_overlay`/`main` → `fetch_speed_lines_config`) keep resolving via the worker re-export → posting and config-fetch behavior identical to pre-split.
- US-2: the TTL caches stay coherent across the split — a staying reader (`crossing_overlay_summary`) sees the mover's cache refreshes because both names bind to ONE dict object (identity re-export); the cache-identity unit test pins `worker.<cache> IS worker_transport.<cache>` for all three caches.
- US-3: a test injects a fake `fetch_crossing_line_config` into an exec namespace (test_line_crossing pattern) → the injected fake replaces the re-export binding in the worker's namespace → staying callers still see the fake; ns-injection patches survive the move (C-4 analysis: no patch-target transfers were needed this wave — attribute-based patches like ubuntu_worker_entrypoint's `_ORIGINAL_POST_STATE = worker.post_state` resolve through the re-export to the same function object).
- US-4: CI/validators run → the exact-artifact required lists (ubuntu-worker AND edge), validate_repo REQUIRED_FILES and the installer's prepared-release check all include worker/worker_transport.py → a payload missing the transport module fails closed at CI or install, never at boot.
- US-5: the compatibility gate's four-file union → REQUIRED_ENV_NAMES all resolve (SEA_SPEED_API_URL/SEA_SPEED_API_TOKEN now read via env_str INSIDE worker_transport — verified in the union); a missing worker_transport.py fails closed.
- US-6: a future contributor adds `import cv2` (or numpy/ultralytics/av/subprocess/socket) to worker_transport.py module level → the import-allowlist + offline-layers tests fail in CI instead of silently coupling the transport layer to render/model/spawn surfaces.
