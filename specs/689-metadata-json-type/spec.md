# Spec: metadata JSON type — reject non-object JSON at the analytics ingestion boundary

- Issue: #689

## Product outcome
Issue #689 closes a crash class in the analytics ingestion API. Four handlers in `api/app/main.py` parse the `metadata` form field with `json.loads(metadata)` and then use the parsed value as a mapping: `post_cam1_passage` (POST /api/cam1/passages) and `api_post_crossing` (POST /api/analytics/{camera_id}/crossings) already rejected a parsed non-object with `400 "metadata must be a JSON object"`, while `post_analytics_state` (POST /api/analytics/{camera_id}/state) and `post_analytics_event` (POST /api/analytics/{camera_id}/events) did not. A syntactically valid non-object document — `[]`, `null`, `42`, `"str"` — therefore passed the `except` clause and crashed the handler: `data["camera_id"] = camera_id` raised `TypeError` in the state handler and `event.get("event_id")` raised `AttributeError` in the events handler, each surfacing as an unhandled 500. The change adds exactly two guards mirroring the two that already existed, so all four `json.loads(metadata)` sites answer a client error instead of a server error. Every affected endpoint is behind worker authentication (`require_auth` runs before the parse, `analytics_identity` runs before the parse in both handlers), so this is input-validation hardening, not an auth bypass: the contract being restored is "malformed or wrongly shaped metadata is the client's 400, never the server's 500". No other source change ships.

## User scenarios
- A worker posts `metadata=[]` to `POST /api/analytics/cam1/state` with a valid bearer token: the handler parses the JSON, sees a list, and answers `400 {"detail": "metadata must be a JSON object"}`; no camera state is written and no 500 traceback reaches the client.
- A worker posts `metadata=null`, `42` or `"str"` to `POST /api/analytics/cam1/events` with a valid bearer token and a snapshot file: the handler parses the JSON, rejects the non-object before the `#587` non-finite scan and before `event.get(...)`, and answers 400; nothing is persisted to the event feed.
- A worker sends a truly malformed body such as `{not json`: the pre-existing `except` clause still answers `400 "metadata must be valid JSON"` on both endpoints — the new guard sits after that clause and does not change it.
- A worker sends a valid JSON object: the request behaves exactly as before — state is upserted and served back through `GET /api/analytics/cam1/state`, an event is delivered and served back through `GET /api/analytics/cam1/events`, duplicate detection is unchanged, and an authenticated worker without the bearer header still gets `403 {"detail": "Forbidden"}` with no write.
- A maintainer reads the source: every `json.loads(metadata)` site in `api/app/main.py` is followed by an `isinstance(<var>, dict)` rejection within a short window, and a source-level test fails loudly if a future parse site lands without one or if the count of known sites drops below four.

## Requirements
1. State guard: in `post_analytics_state` (POST /api/analytics/{camera_id}/state), immediately after the existing `try`/`except` parse block and before `data["camera_id"] = camera_id`, add `if not isinstance(data, dict): raise HTTPException(status_code=400, detail="metadata must be a JSON object")`.
2. Events guard: in `post_analytics_event` (POST /api/analytics/{camera_id}/events), immediately after the existing `try`/`except` parse block and before the `#587` non-finite scan and `event.get("event_id")`, add the same `isinstance` guard for `event`.
3. Mirror, do not invent: both guards use the exact shape already present in `post_cam1_passage` and `api_post_crossing` — same condition, same status 400, same detail string `metadata must be a JSON object` — so the four sites are consistent and the anti-vacuity source test can find them by one idiom.
4. Auth order unchanged: `require_auth(authorization)` and `analytics_identity(camera_id)` keep running before the parse in both handlers; the guard adds a check after authentication and grants no path that was previously denied.
5. Malformed JSON unchanged: the existing `except Exception: raise HTTPException(status_code=400, detail="metadata must be valid JSON")` clause stays the first rejection for unparseable bodies on both endpoints.
6. Side effects preserved for valid objects: state upsert, overlay handling, both `#587`/`#617` non-finite scans, event normalization, duplicate detection and delivery are untouched, so a valid object request yields the same response body and the same persisted state as before.
7. Bounded surface: no other source file changes; the only test changes are the new `tests/test_689_metadata_json_type.py` plus two test-infrastructure fixes — the import-hygiene oracle entry list in `tests/test_run_tests_script.py` for the three new guarded-optional imports, and the new file's `sys.modules` snapshot taken in `setUpClass` instead of at module import time.
8. One-process battery safety: the new test class snapshots `sys.modules` immediately before its app import and restores exactly that pre-import state at class cleanup, and evicts the `api.app.*` names it introduced, so later tests in the same process (notably `tests/test_api_http_integration.py`) re-import against their own environment and are not left with a stale `api.app.main`.

## Acceptance criteria
- AC-001: a non-object JSON metadata payload (`[]`, `null`, `42`, `"str"`) posted to POST /api/analytics/{camera_id}/state and POST /api/analytics/{camera_id}/events with a valid worker token answers 400/422, never 500, and the response body contains no traceback.
- AC-002: malformed JSON still answers 400/422 on both endpoints, valid JSON object payloads keep their existing side effects (state round-trips through GET, event is delivered and served back, duplicate flag unchanged), and the permission boundary holds — a request without the Authorization header answers 403 with no write.
- AC-003: all four `json.loads(metadata)` sites in `api/app/main.py` have a nearby `isinstance(<var>, dict)` rejection, pinned by a source-level test that finds at least the four known sites and fails on any unguarded one.
- AC-004: the full Python battery and every validator stay green (1439 tests OK with skipped=2; repo/contracts/quality/workflow/token validators PASS; ruff PASS), and the new test does not corrupt `sys.modules` for other tests in the same process.

## Runtime feedback
- Incident (input-validation class, issue #689): correct JSON of the wrong type — `[]`, `null`, `42`, `"str"` — reached `.get()` and key assignment in two analytics handlers, producing `AttributeError`/`TypeError` and an unhandled 500. The two sibling handlers already had the guard, so the defect is an inconsistency at the boundary, not a missing contract.
- Risk shape that made this worth a change: a 500 on client-controlled input is a reliability and observability defect (error-rate noise, misleading incident signal) even though the endpoints are authenticated; the fix restores the stated contract rather than adding a new one.
- Implementation feedback: mirroring the two existing guards was load-bearing — the same condition, 400 and detail string keep the four sites consistent and make the source-level test a single-idiom scan. The guard must sit after the parse `except` (otherwise it would shadow the "must be valid JSON" message) and before the first dict operation (otherwise the crash still happens).
- Test-harness feedback: the new HTTP tests use the established authenticated-worker fixture pattern (`SEA_SPEED_API_TOKEN` fixture value plus `Authorization: Bearer`, the real `require_auth`) with `TestClient(..., raise_server_exceptions=False)` so the pre-fix 500 is observed as an HTTP response; no auth bypass and no stubbed identity. RED before the fix: 9 failed / 6 passed; GREEN after: 7 passed plus 8 subtests.
- One-process battery feedback: two infrastructure fixes were needed and are part of the diff. The import-hygiene oracle in `tests/test_run_tests_script.py` is an exact-match list, so the three new guarded-optional import entries had to be declared. And the new file must snapshot `sys.modules` in `setUpClass` immediately before its import, not at module import time: discovery imports `tests/test_617` after this module, so the module-time snapshot went stale and the full battery produced 4 errors plus 1 failure inside `tests/test_api_http_integration.py`. The per-class snapshot/restore makes the full battery green (1439 tests OK, skipped=2).
