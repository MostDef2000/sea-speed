# Spec: wave-8 worker tracking — tracking-cluster extraction (move-only)

- Issue: #397
- Specification: specs/397-wave8-worker-tracking/spec.md

## Product outcome

Waves 1-7 extracted the pure kernel, the media/reader layer, the cv2 render/snapshot layer, the requests transport/posting layer (waves 4-5), the crossing analytics domain (wave 6) and the live-publisher family (wave 7); the worker still mixes the per-track speed-tracking cluster with the ROI family, the speed-lines overlay and the supervision main loop. Wave 8 extracts the tracking cluster verbatim (move-only, byte-identical bodies) into NEW `worker/worker_tracking.py`: the 3 per-track speed state literals (`_speed_track`, `_track_states`, `_line_speed_state`) and the 8 tracking defs (`detection_center_px`, `update_speed_estimate`, `convert_px_s_to_kmh`, `update_speed_lines_estimate` — whose nested helpers (`median_value`, `update_sample_metadata`, `apply_held_speed`, `valid_line`, `midpoint`, `progress_m_from_calibration`) move with it — `track_event_posted`, `mark_track_event_posted`, `water_event_candidates`, `prune_track_states`) — ONE contiguous region (479-739 at main f9d4f37) cut in a single pass with the standing blank-pair discipline.

The wave's central mechanism is the purity of the tracking math: the moved bodies resolve exactly from stdlib `time` plus the repo siblings worker_kernel (`env_float`, the DETECTION_* tunables) and worker_transport (`fetch_speed_config`, `fetch_speed_lines_config`, the calibration configs) — NO cv2/numpy (unlike the ROI/render surfaces that stay), NO threading/queue (unlike the wave-7 publisher), NO datetime/ultralytics/av/subprocess/socket/requests/json/pathlib/os. Object-identity coupling: the three state dicts are defined ONCE in worker_tracking and re-exported BY IDENTITY — nothing in the whole worker source set rebinds them (every access is an in-place mutation — `dict[key] = ...`, `.clear()`, `.update()` — or a read of the same dicts), so the estimators and the staying worker callers share ONE state. All three state names are strictly non-rebinding (unlike wave 7's `_LIVE_PUBLISH_THREAD`, there is NO rebinding name in the cluster — the AST Store guard covers all three, and no `global` statement anywhere names any of the 11 moved names). The worker re-exports all 11 moved names via a flat sibling ImportFrom: the supervision main loop's call sites (`update_speed_estimate`, `update_speed_lines_estimate`, `convert_px_s_to_kmh`, `prune_track_states`, `water_event_candidates`, `track_event_posted`, `mark_track_event_posted`) and the staying `build_event` (which calls `convert_px_s_to_kmh`) keep resolving them through the worker's flat namespace.

Deliberate STAYS in the worker (recorded, not silently dropped, with forced reasons):
- `_roi_processing_points`, `prepare_roi_processing_frame`, `detection_inside_road_roi`, `roi_processing_signature`, `draw_roi_polygon`, `parse_road_roi_polygon`, `road_roi_enabled` — the ROI family: `_roi_processing_points` REBINDS via `global` + assignment and the family's callees are cv2/numpy (off the tracking import allowlist by construction).
- `draw_speed_lines_overlay` — the speed-lines render surface: it reads only `fetch_speed_lines_config` + cv2 and NONE of the moved names, and has no production callers; its placement is pinned (present in the worker, absent from worker_tracking).
- `detect_vehicles`, `build_road_live_envelope`/`build_water_live_envelope`, `build_event`, `main` and the MotionDetector class — the supervision main loop and its callees (cv2/numpy/ultralytics domain) are outside the tracking cut.

Convergence is fail-closed everywhere the new deployable ships: the compatibility gate's `MODULE_SOURCES` extends 6→7 (seven-file union, semantics unchanged), `validate_repo` REQUIRED_FILES, `build_exact_artifacts` (ubuntu-worker AND edge), `validate_exact_artifacts` (ubuntu-worker AND edge) and the installer's prepared-release required loop all gain `worker/worker_tracking.py`, so a payload missing the flat sibling fails at CI or install — never silently at boot. NO dead imports arise this wave (unlike wave 7): `time`, `env_float`, `fetch_speed_config`/`fetch_speed_lines_config` all retain staying users in the worker (the live GENERATION stamps, the ROI/diagnostic tunables, `draw_speed_lines_overlay`), so the worker's import surface only GAINS the flat sibling re-export.
