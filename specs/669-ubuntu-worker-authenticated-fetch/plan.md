# Plan: Ubuntu Worker authenticated fetches (private-repo worker contour)

- Specification: specs/669-ubuntu-worker-authenticated-fetch/spec.md

## Architecture
Four surfaces, one mechanism: (1) `scripts/operations/sea_speed_ubuntu_zero_touch_gate.sh` root mode reads and validates the root-owned read token (exists, mode 600, root-owned, non-empty → `fail`) immediately before its staging fetch and authenticates that fetch with an env-fed inline git credential helper; (2) `deploy/worker/ubuntu/deploy-authorized.sh` moves its existing token validation block ahead of the staging fetch and authenticates the fetch the same way; (3) `deploy/worker/ubuntu/update-exact.sh` reads the token before its staging fetch and uses the same token instance for the authenticated fetch and the `verify_quality_status.py` provenance check; (4) `.github/workflows/deploy-ubuntu-worker.yml` drops `persist-credentials: false` so the composite's post-checkout `git fetch` authenticates. The policy-doc clause names all three shell entrypoints. The composite action, VPS contour, router and the gate's unprivileged mode are untouched.

## Decisions
- Transport mechanism: env-fed inline credential helper — `SEA_SPEED_GITHUB_READ_TOKEN="$github_token" git -c credential.helper= -c 'credential.helper=!f() { printf "username=x-access-token\n"; printf "password=%s\n" "$SEA_SPEED_GITHUB_READ_TOKEN"; }; f' fetch ...`. The token value exists only in the git process environment (the scripts already run as root, the only account that can read the 600 root-owned token file) and in the helper's stdin/stdout protocol pipe — never in argv, URLs, git config or error text. URL embedding was rejected outright (token in argv + persisted in the stage's git config); `http.extraHeader` was rejected because the expanded header value lands in argv (`ps` exposure). The mechanism was live-probed with `git credential fill` before implementation.
- The leading empty `-c credential.helper=` reset is REQUIRED, not cosmetic: with multiple helpers configured, a host-global helper (e.g. `credential.helper=store`) would otherwise answer the credential query and receive the token via the approve action, persisting it to disk. The reset empties the helper chain so only the inline helper runs; the probe proved a global helper answers when the reset is absent.
- Gate validation placement: inside `execute_root()`, after stage creation and before the fetch, so the existing executed stage-cleanup error-path test keeps its exact scenario (failure after stage creation, trap cleanup). The gate's `fail()` (exit 1) semantics are reused; the unprivileged entrypoint/protocol mode is untouched.
- Gate token constant `GITHUB_READ_TOKEN_FILE=/etc/sea-speed/github-read-token` mirrors the deploy scripts' default `token_file`; the gate runs as root via the sudo rule, so it can read the 600 root-owned file. `stat` joins the gate's required-command list for the mode/owner checks.
- deploy-authorized.sh MOVES its existing validation block (no duplicate checks) so exit-5 semantics and messages stay byte-identical; update-exact.sh keeps its file-level validation where it already was (before the fetch) and moves only the content read + empty check ahead of the fetch.
- The executed gate harness (`_gate_execute_root_source`) gains one documented mechanical adaptation: the token-file constant is redirected into the fixture and the root-ownership line is dropped (a fixture file cannot be root-owned without root; the ownership check stays pinned structurally). The existing fetch-failure cleanup test creates a valid fixture token so its scenario (fetch failure, not token failure) is preserved.
- The workflow fix is the #668 precedent applied verbatim: REMOVE `persist-credentials: false` rather than setting `true` (absent = actions/checkout default = persist); the composite action itself is untouched.
