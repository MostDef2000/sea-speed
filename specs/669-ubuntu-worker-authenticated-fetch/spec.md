# Spec: Ubuntu Worker authenticated fetches (private-repo worker contour)

- Issue: #669

## Product outcome
The repository is private (owner action 2026-11-13, trust model fixed for the VPS contour in #668) and the Ubuntu Worker deploy contour still assumed public-source access: the zero-touch gate's root-mode fetch, `deploy/worker/ubuntu/deploy-authorized.sh`'s staging fetch and `deploy/worker/ubuntu/update-exact.sh`'s staging fetch were anonymous, the worker workflow checkout disabled credential persistence so the composite post-checkout `git fetch` could not authenticate, and the root-owned read token was validated but never used for git transport (deploy-authorized.sh) or used only for the provenance check (update-exact.sh). The outcome: every fetch on the Ubuntu Worker deploy path — the gate's root-mode fetch, the deploy transaction's staging fetch, the exact updater's staging fetch and the composite's post-checkout fetch — authenticates with the existing root-owned `/etc/sea-speed/github-read-token` (no new secrets, token stays on-host, pointer-only), each fetch fails closed when the token is missing/invalid BEFORE any network transport, and the token value never enters argv, URLs, git config or logs. Governing docs no longer claim public visibility for the worker contour.

## User scenarios
- An allowed Ubuntu Worker deploy on the private repository reaches the worker through the forced-command gate; the gate's root-mode fetch authenticates with the root-owned read token, the exact-artifact digest is recomputed, and `deploy-authorized.sh` re-fetches authenticated for its own staging and exact-update transaction — no anonymous transport anywhere on the path.
- A worker host without the root-owned token file (missing, wrong mode, wrong owner or empty) fails closed with the established exit-5/error semantics BEFORE any network fetch, in the gate and in both deploy scripts.
- The protected `deploy-ubuntu-worker.yml` run checks out with credential persistence so the shared composite's post-checkout `git fetch --no-tags origin ...` authenticates with the job-scoped `GITHUB_TOKEN`.

## Requirements
1. `scripts/operations/sea_speed_ubuntu_zero_touch_gate.sh` root mode reads and validates the root-owned read token (file exists, mode 600, owned by root, non-empty; `fail` semantics) BEFORE the staging fetch, and the fetch authenticates through an env-fed inline git credential helper (leading empty `credential.helper=` reset, helper reads the token from its process environment); the token never appears in argv, URLs, git config or logs, and the variable is unset after the fetch. The unprivileged syntax-validation/protocol mode is untouched.
2. `deploy/worker/ubuntu/deploy-authorized.sh` moves the existing token read+validation block BEFORE the staging fetch (exit-5 semantics unchanged), uses the token for the fetch via the same env-fed credential helper, and unsets it after use as today.
3. `deploy/worker/ubuntu/update-exact.sh` reads the token before the staging fetch, uses the same token instance for BOTH the authenticated fetch and the `verify_quality_status.py` provenance check, and unsets it after the provenance check.
4. `.github/workflows/deploy-ubuntu-worker.yml` checkout keeps credential persistence (no `persist-credentials: false`) so the composite `.github/actions/verify-exact-release` post-checkout `git fetch` authenticates; the composite action itself is NOT changed.
5. Contract tests pin the authenticated fetch path in all three shell entrypoints (token validation precedes the fetch; the fetch consumes the token through the env-fed credential helper with the empty reset preceding the inline helper; no credentials in argv/URL; token unset after use) and the workflow checkout credential persistence; the executed gate error-path test proves a missing token fails closed before any fetch and the existing stage-cleanup behavior is unchanged.
6. `contracts/SEA_SPEED_DELIVERY_POLICY.md` no longer claims the worker contour re-fetches "public main": the gate's and the deploy transaction's repository fetches authenticate with the root-owned GitHub read token.

## Acceptance criteria
- AC-001: tests.test_ubuntu_worker_deploy_authorized proves the deploy-authorized.sh contract — token validation precedes the first fetch, the fetch consumes the token through the env-fed credential helper (empty reset first, no URL/argv credentials), and the token is unset after use.
- AC-002: tests.test_ubuntu_worker_exact_updater proves the update-exact.sh contract — token read precedes the fetch, the same token serves the fetch and the provenance check, identical no-exposure pins, unset after the provenance check.
- AC-003: tests.test_ubuntu_zero_touch_transport proves the gate contract — the root-mode fetch authenticates through the env-fed credential helper with validation before the fetch (structural pins), a missing token fails closed before any fetch while the stage-cleanup trap still fires (executed), the existing fetch-failure cleanup path is preserved, and the delivery policy no longer claims "re-fetches public".
- AC-004: tests.test_autonomous_execution_policy proves the deploy-ubuntu-worker.yml checkout keeps persisted credentials for the composite post-checkout `git fetch`.
- AC-005: `bash -n` on all three changed shell scripts, the validate gates mirrored from quality-integration.yml (validate_sdd, validate_repo, validate_contracts, validate_quality_contracts, validate_workflow_policy, validate_token_preflight, py_compile, ruff) and the full unittest battery are green; `git diff --stat` shows only the allowed paths.
