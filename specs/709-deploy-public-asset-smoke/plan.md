# Plan: deploy public-asset smoke — a strict 200-only verifier for the public web-root helper

- Spec: specs/709-deploy-public-asset-smoke/spec.md

## Architecture
One deploy-script change plus additive tests, no new file in the deploy path. `deploy/vps/deploy.sh` gains a top-level `verify_public_asset_200()` immediately after `verify_public_url()`: it captures `%{http_code}` with the same curl options as the permissive helper, treats a curl failure as a hard failure, returns 1 on any status other than `200` with `<label> public asset smoke check failed with HTTP ${status}: ${target}` on stderr, and on `200` logs both the legacy `<label> public smoke check passed with HTTP 200` line and the distinct `<label> public asset smoke check passed with HTTP 200` line. The login-popup smoke block inside `verify_frontends` switches from `verify_public_url "Login popup module" "$LOGIN_POPUP_URL"` to `verify_public_asset_200 "Login popup module" "$LOGIN_POPUP_URL" || return 1`, keeping the existing `[[ -f "$LOGIN_POPUP_TARGET" ]]` presence guard and its "absent in this rollback release" branch. The failure chain is unchanged code that now receives a non-zero: `verify_frontends` returns 1, `restart_and_verify` returns 1, the main transaction's `if restart_and_verify` is false, and the script reinstalls the previous release, re-verifies it through the same `restart_and_verify`, writes the `rolled_back` manifest and logs `Rollback successful`. `verify_public_url()` and every other frontend check stay byte-identical. `tests/test_vps_deploy_transaction.py` gains three additive tests: a source pin that a dedicated strict verifier exists and that `verify_public_url` was not tightened, a source pin that the login-popup block calls it, and a behavioral test whose fake curl answers per-URL statuses (302/401/403/404 must fail closed and roll back, 200 must pass with the distinct line).

## Decisions
- A dedicated `verify_public_asset_200()` helper instead of tightening `verify_public_url()`: the permissive set `200|301|302|307|308|401|403` is the correct contract for the operator assets behind authentik, so the strict 200-only rule is scoped to the one public web-root helper that must be anonymously readable. Tightening the shared helper would break every protected asset check.
- Emit BOTH the legacy pass line and the distinct strict line on 200: existing success-smoke assertions match `<label> public smoke check passed with HTTP 200`, so the strict helper keeps that line and adds `<label> public asset smoke check passed with HTTP 200` to name the new contract without weakening or rewriting existing assertions.
- Explicit `|| return 1` at the login-popup call site: `verify_frontends` ends with a permissive root-frontend check whose status is the function's exit status, so a non-zero from the middle of the function would otherwise be masked; the explicit return makes the failure the function's result.
- Source pins in addition to behavioral coverage: behavior proves the call site fails closed, but only a source pin proves a dedicated reusable verifier exists (the call site could inline an equivalent check) and that `verify_public_url` was not tightened. Both pins are additive and state that reason in their comments.
- Per-URL fake curl keyed on the live helper content: the rollback path re-runs `restart_and_verify` against the previous release, so the fake login-popup answer must return to a healthy 200 after the swap; keying it on the helper content the test can observe keeps both the injected failure and the rollback re-verification honest.
- Tests are additive only: the three new tests are appended to `tests/test_vps_deploy_transaction.py`; no existing test or assertion is changed, so AC-004 is provable by the unchanged battery plus the new cases.
- No workflow, nginx, auth or frontend edit: the defect is in the deploy transaction's verification logic, so the smallest complete change is the script plus its tests. The production asset itself (wave 2 / login popup release) is deployed by the normal lane, not by this change.
- Change Contract declaration is load-bearing: `deploy/vps/deploy.sh` is in the diff, so the autonomous policy derives `VPS deployment: REQUIRED` from the path. The PR Change Contract must therefore declare `Production impact: VPS`, `VPS deployment: REQUIRED`, `VPS execution capability: CONNECTOR`, `Ubuntu worker/relay update: NOT REQUIRED`, `Ubuntu worker execution capability: NOT APPLICABLE`, `Production safety envelope: REQUIRED` and `Operator actions expected: 0`; an undeclared or contradicting contract is rejected before merge.

## Runtime feedback
- The miss was structural, not incidental: `verify_public_url()` treats 302/401/403 as success for protected assets, which is exactly the status family an absent public file can produce behind an auth gate, and the trailing permissive root-frontend check inside `if restart_and_verify` turned any earlier non-zero into an ignored value.
- Production evidence: `https://mostdef.ru/login-popup.js` returned 404 while `https://mostdef.ru/unavailable.js` returned 200 — the public helper was missing from the deployed release and no existing gate reported it.
- The two skipped deploys (PR #708 wave 2 and PR #711 login popup) were the second half of the incident: after the authentik outage the last main commit (#684) was CI-only with `VPS deployment: NOT REQUIRED`, so the autonomous deploy policy found no VPS contour. That policy behaviour is correct; the missing piece was the deploy-time public-asset smoke.
- Implementation feedback: the dual success line exists because the legacy assertions match the old text; the source pins exist because behavioural coverage alone cannot distinguish a dedicated reusable verifier from an inline check or prove that the permissive helper was left alone.
