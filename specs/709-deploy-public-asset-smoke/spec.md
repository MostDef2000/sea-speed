# Spec: deploy public-asset smoke — a strict 200-only verifier for the public web-root helper

- Issue: #709

## Product outcome
Issue #709 closes a detection gap in the VPS deploy transaction. `deploy/vps/deploy.sh` verified every frontend URL with `verify_public_url()`, which accepts `200|301|302|307|308|401|403` as success — correct for the protected operator assets behind authentik, wrong for a public web-root helper that must be anonymously readable. When `https://mostdef.ru/login-popup.js` returned 404 in production (observed while `https://mostdef.ru/unavailable.js` returned 200), the deploy smoke could not tell the difference, and even a rejected status inside `verify_frontends` was swallowed by the trailing root-frontend check inside `if restart_and_verify`. This change adds a dedicated strict verifier, `verify_public_asset_200()`, that accepts ONLY HTTP 200 and fails closed with an explicit error; the login-popup smoke block calls it, so a non-200 propagates `verify_frontends` → `restart_and_verify` → the main transaction's rollback path (`rolled_back` manifest, `Rollback successful`) instead of ending in a green deploy. `verify_public_url()` stays byte-identical, so protected assets keep accepting 302/401/403. The change is deploy-script logic plus additive regression tests; no workflow, nginx, auth or frontend source is touched.

## User scenarios
- A developer opens a pull request that ships `frontend/sea-speed/login-popup.js`, the deploy runs the healthy-path smoke, and the helper answers anonymously with HTTP 200: the deploy logs both the legacy `<label> public smoke check passed with HTTP 200` line and the distinct `<label> public asset smoke check passed with HTTP 200` line, then continues to a `runtime_verified` manifest.
- The public web-root helper regresses to a non-200 (the production shape: `/login-popup.js` 404 while `/unavailable.js` 200): the deploy fails closed, prints `Login popup module public asset smoke check failed with HTTP 404: https://mostdef.ru/login-popup.js`, rolls the release back to the previous commit, writes the `rolled_back` manifest and logs `Rollback successful`, so the regression is visible in the deploy run instead of being counted as a passed smoke check.
- A protected operator asset behind authentik answers 302, 401 or 403 during a healthy deploy: the deploy still passes, because `verify_public_url()` remains permissive and is untouched — the strict rule applies only to the public web-root helper.
- An operator or the autonomous deploy policy inspects the release: `verify_frontends` returns non-zero on a strict public-asset failure, so `if restart_and_verify` is false and the trailing root-frontend check can no longer mask the failure; the failure reason is in stderr and the deploy exits non-zero with the rollback evidence.

## Requirements
1. Dedicated verifier: `deploy/vps/deploy.sh` defines a top-level `verify_public_asset_200()` immediately after `verify_public_url()`, using the same curl shape (`--silent --show-error --output /dev/null --write-out '%{http_code}' --max-time 15`) and accepting ONLY `200`.
2. Fail-closed error: any other status prints `<label> public asset smoke check failed with HTTP ${status}: ${target}` to stderr and returns 1; a curl transport failure prints `<label> public asset smoke check request failed: ${target}` to stderr and returns 1.
3. Dual success line: on HTTP 200 the helper logs BOTH the legacy `<label> public smoke check passed with HTTP 200` line (kept for the existing success-smoke assertions) and the distinct `<label> public asset smoke check passed with HTTP 200` line that names the strict contract.
4. Permissive verifier preserved: `verify_public_url()` is byte-identical — it still accepts `200|301|302|307|308|401|403` and still logs its existing pass line, because the protected operator assets legitimately answer 302/401/403 behind authentik.
5. Login-popup call site: the login-popup smoke block inside `verify_frontends` calls `verify_public_asset_200 "Login popup module" "$LOGIN_POPUP_URL" || return 1`; the permissive `verify_public_url "Login popup module" "$LOGIN_POPUP_URL"` call is gone, and the block stays guarded by the existing `[[ -f "$LOGIN_POPUP_TARGET" ]]` presence check with its rollback-release absent branch.
6. Unmasked propagation: on a non-200 the failure returns non-zero out of `verify_frontends`, so `restart_and_verify` fails, the main transaction's `if restart_and_verify` is false, the script reinstalls the previous release, re-verifies it, writes the `rolled_back` deployment manifest and logs `Rollback successful`, exiting non-zero.
7. Regression tests: `tests/test_vps_deploy_transaction.py` gains three additive tests — a source pin that a dedicated strict 200-only verifier exists and that `verify_public_url` was not tightened, a source pin that the login-popup block calls the strict helper, and a behavioral test that injects per-URL statuses 302/401/403/404 (each must fail closed with rollback) plus 200 (must pass with the distinct log line).
8. Bounded surface: no other file under `deploy/**` changes, no workflow changes, no nginx/auth/frontend change, no existing test assertion is weakened, and `bash -n deploy/vps/deploy.sh` is clean.

## Acceptance criteria
- AC-001: `deploy/vps/deploy.sh` defines a dedicated strict public-asset verifier that accepts only HTTP 200, and the permissive `verify_public_url` still accepts `200|301|302|307|308|401|403` unchanged (no tightening of the protected-asset path).
- AC-002: the login-popup smoke block calls the strict verifier, and on HTTP 200 the deploy log contains both `Login popup module public smoke check passed with HTTP 200` and `Login popup module public asset smoke check passed with HTTP 200`.
- AC-003: a 302, 401, 403 or 404 for the login-popup URL fails the deploy closed — non-zero exit, `rolled_back` manifest, `Rollback successful`, and an error naming the label and the HTTP status — and the failure is not swallowed by the trailing root-frontend check.
- AC-004: the full Python battery and every validator stay green (1432 tests OK with skipped=2, repo/contracts/quality/workflow/token validators PASS, ruff PASS, `bash -n` OK) with no existing assertion weakened.

## Runtime feedback
- Incident (P1, issue #709): after an authentik outage `https://mostdef.ru/sea-speed/*` returned 502. The owner restored authentik (the operator page answers the 302 auth gate again), but the deploys for PR #708 (wave 2) and PR #711 (login popup) had been skipped — first because of the outage, then because the last main commit (#684) was CI-only with `VPS deployment: NOT REQUIRED`, so the autonomous deploy policy saw no VPS contour to deploy.
- Production evidence that the smoke could not see: `https://mostdef.ru/login-popup.js` returned 404 while `https://mostdef.ru/unavailable.js` returned 200 — the public helper was absent from the deployed release and every permissive status would have been reported as a passed check.
- Root cause of the missed detection: `verify_public_url()` accepts `200|301|302|307|308|401|403` (correct for authentik-protected assets, wrong for the public web-root helper), and a failure raised inside `verify_frontends` was swallowed by the trailing root-frontend check that ran inside `if restart_and_verify`.
- Implementation feedback: the dual success line is load-bearing — existing assertions match the legacy `<label> public smoke check passed with HTTP 200` text, so the strict helper emits it as well as its distinct line; tightening `verify_public_url` instead of adding a helper would have broken the protected-asset contract, which is why a separate helper is pinned by test.
- Test-harness feedback: the behavioral test branches the fake curl per URL and keys the login-popup answer on the live helper content, so the in-script rollback re-verification of the previous release sees a healthy 200 again and the test can assert both the failure and the successful rollback.
