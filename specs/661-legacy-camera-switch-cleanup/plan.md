# Plan: legacy VPS camera-source-switch cleanup + fail-closed relay-identity config install

- Spec: specs/661-legacy-camera-switch-cleanup/spec.md

## Architecture
Both transcode scripts gain the camera-relay.sh post-#449 permission contract at the same seam: after the digest gates and the `id sea-speed` readiness gate, BEFORE the backup, activate calls the ported `derive_relay_service_identity()` (verbatim port; `$relay_service` instead of `$service_name`), prints `INSTALL_OWNER=`/`MODE=` evidence, and refuses with exit 9 on derivation failure. The config install consumes the derived owner/group/mode; the unit install and camera1's watchdog installs move behind `--systemd-unit-dir` / `--watchdog-bin-dir` seams (defaults = the production paths, so existing invocations are unchanged). The legacy `deploy/vps/camera-source-switch.sh` is deleted outright (dead VPS-mediamtx-era tooling; its canonical-cam1 duties were absorbed by the #335/#659-era flows and the road1-720p transcode path, PR #660) and the four runbooks keep the history as marked removal notes. The contract is pinned by executed twins: the real script bytes run from a copy tree (real renderer bytes planted executable, since the repo-tracked renderer is 100644) under `unshare --user --map-root-user`, with systemctl stubbed always and `id`/`install` stubbed OPT-IN (environment readiness only).

## Decisions
- Verbatim port of `derive_relay_service_identity` (only `$service_name` → `$relay_service` and the comment header adapted): the contract is proven on the box since #449; diverging idioms would create a second identity contract to maintain.
- The caller block sits AFTER the id gate and BEFORE the backup: evidence precedes every mutation, and a failed derivation must not leave a backup or partial install behind (exit 9, nothing written).
- Backup line stays hardcoded `root:root 0600` into the root-only state dir: the backup is operator-recovery material owned by root, not relay-readable state — identical to camera-relay.sh.
- `--systemd-unit-dir` / `--watchdog-bin-dir` seams: they make the transaction testable in a user namespace (the sandbox cannot write the real `/etc/systemd/system` or `/usr/local/sbin`) and cost nothing in production (defaults are the production paths); unit-file content, restart/rollback blocks and exit codes 7/8/30-33 are untouched.
- Executed twins over source-text pins (issue #398 wave-3 discipline): the twins run the REAL script bytes and assert the install stub's argv log, so the proof is that the real install line consumed the derived identity — not that a string exists in the source.
- Opt-in `id`/`install` stubs in tests/support/relay_shell.py (default OFF, every existing suite keeps the real coreutils tools): the sandbox has no `sea-speed` user and no `mediamtx` group, and a single-uid user namespace cannot chown to a non-root group at all (observed EINVAL; nonexistent groups fail earlier with "invalid group"). Both stubs cover environment readiness, not the behavior under test; the install stub records full argv to `$INSTALL_LOG` and applies the requested mode for real (copy + chmod), keeping mode assertions honest.
- Scenario (c) is entirely flag-free: post-fix the derivation refuses before any install, so the redirects are never reached; on base the flag-free run executes deeper (past the digest and id gates, takes the backup, dies at the hardcoded real-`/etc` unit install) — a behavioral RED that detects the missing fail-closed contract rather than a missing flag.
- Scenarios (a)/(b) fail on base via `unknown option: --systemd-unit-dir` (parse-time refusal): the RED is still authentic (the tests cannot pass on base); a base full-activate is environmentally impossible anyway.
- Deletion over deprecation for the legacy script: nothing references it outside historical specs (075/076) and the four runbooks; the runbooks keep the historical command shapes as record inside the removal notes (mark, never erase history).
