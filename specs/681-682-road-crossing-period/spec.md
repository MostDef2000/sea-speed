# Spec: road crossing period filter drives the panel and the last-crossing time becomes truthful

- Issue: #681
- Issue: #682

## Product outcome
The road page crossing panel (`frontend/sea-speed/road/index.html` + `frontend/sea-speed/road/main.js`) gets a working period filter and a truthful last-crossing line. For #681, `#cxShowBtn` ("Показать") previously called `refresh()` (state+events) and never the summary endpoint, so the date inputs were dead UI; now `loadCrossingStats()` reads `#cxFrom`/`#cxTo`, rejects an inverted range client-side with an error row and no request, otherwise fetches `/sea-speed/api/analytics/road1/crossings/summary?date_from=..&date_to=..` once, renders `totals`/`by_class` into the KPIs and the per-class table, labels `#cxMode` with the applied range, and switches `crossingStatsMode` to `"period"` so the 3-second state refresh no longer overwrites the panel; a stale-response guard (`crossingStatsRequestSeq`) prevents an older response from committing, and the new `#cxLiveBtn` ("Текущее") returns to live mode and restores the state counts. Date defaults are Vladivostok today (`vlzToday()`, UTC+10), not UTC. For #682, the browser-clock line (`cxLast.textContent=new Date().toLocaleTimeString()`) is deleted: the API summary returns an additive `last_crossing_at` — the maximum parsed `created_at` among records that pass the window filter AND have a valid direction, `null` when none — and the frontend renders it in Asia/Vladivostok with date+time, or «Нет данных» when null/invalid; in live mode the page fetches the summary for VLZ-today on boot and every 15 s solely to keep `#cxLast` truthful, isolated so its failure never affects state/events rendering.

## User scenarios
- An operator on the road page picks a date range and presses «Показать»: exactly one summary request carrying both selected dates goes out, the KPIs (`#cxStatsIn`/`#cxStatsOut`/`#cxStatsTotal`) and the per-class table show the period totals, `#cxMode` labels the applied period, and the 3-second state refresh no longer overwrites the numbers.
- An operator enters an inverted range (from later than to): an error row («Ошибка: дата «с» позже даты «по»») renders immediately and no request is issued; if the summary request itself fails, an error row renders and the previously shown numbers stay.
- An operator reads «Последнее пересечение»: it shows the actual time of the last counted crossing rendered in Vladivostok time (date+time), not the operator's browser clock; when the window has no counted crossings it shows «Нет данных».
- An operator presses «Текущее» (`#cxLiveBtn`): the panel returns to live mode, `#cxMode` shows «текущее состояние», and the next state render restores the live state counts identical to the overlay.

## Requirements
1. Issue #681 — `frontend/sea-speed/road/main.js`: `cxShowBtn.onclick` binds `loadCrossingStats()`; it reads `#cxFrom`/`#cxTo`, and when `from > to` renders the error row and sets `#cxMode` to «период задан неверно» WITHOUT issuing a request; otherwise it issues exactly one fetch to `CROSSING_SUMMARY_URL` (`/sea-speed/api/analytics/road1/crossings/summary`) with `date_from`/`date_to`, renders `totals` into the KPIs and `by_class` (sorted by total, descending) into the table, calls `renderCrossingLast(d.last_crossing_at)`, sets `#cxMode` to the applied range, and sets `crossingStatsMode="period"`.
2. Period-view protection: `renderCrossingStats` — the state-driven renderer used by the 3-second `refresh()` loop — early-returns unless `crossingStatsMode === "live"`, so applied period numbers survive state refreshes; `loadCrossingStats` tags each request with a monotonically increasing `crossingStatsRequestSeq` and discards any response whose sequence no longer matches, so an older response can never commit over a newer one.
3. Return-to-live: `#cxLiveBtn` sets `crossingStatsMode` back to `"live"`, sets `#cxMode` to «текущее состояние», refreshes `#cxLast` and calls `refresh()`, so the next state render restores the state counts.
4. Date defaults: both `#cxFrom` and `#cxTo` default to `vlzToday()` (UTC+10-shifted ISO date) at boot — Vladivostok today, not UTC — matching the API's VLZ day-window semantics.
5. Issue #682 (API) — `api/app/analytics.py`: the crossings summary response gains ONE additive field `last_crossing_at`: the maximum parsed `created_at` instant among records that pass the window filter (VLZ day bounds or rolling-hours cutoff) AND have a valid direction, serialized as a timezone-qualified ISO-8601 string; `null` when no record qualifies; naive record timestamps are treated as UTC; everything else in the response is unchanged.
6. Issue #682 (frontend) — the browser-clock line is deleted; `renderCrossingLast` renders the summary value via `toLocaleString("ru-RU", {timeZone:"Asia/Vladivostok", ...})` as date+time, or «Нет данных» when the value is null/invalid/not a string.
7. Live-mode truthfulness: on boot and every 15 s (`setInterval(refreshCrossingLast, 15000)`) the page fetches the summary for the VLZ-today window solely to keep `#cxLast` current; the fetch is guarded by `crossingStatsMode === "live"` and its failure is swallowed — it never affects state/events rendering.
8. Spec 044 reconciliation: R4/AC-004 of `specs/044-crossing-daily-sync-registry-layer/spec.md` («Panel headline and table read state.crossings (identical numbers to the overlay)») now governs LIVE mode only; the period view is an explicit, user-initiated, visibly labelled exception — `#cxMode` shows the applied period whenever period numbers are on screen — with a return-to-live control (`#cxLiveBtn`). Live-mode behaviour is unchanged.
9. Test contour: new `tests/test_681_682_road_crossing_period.py` (`RoadCrossingPeriodTests`, 9 tests over the road page source and DOM harness); `tests/test_line_crossing.py` extended with `SummaryLastCrossingAtTests` (5 API tests); the existing road executed twin `tests/test_frontend_contract.py` (18 road tests) stays untouched and green.

## Acceptance criteria
- AC-001: clicking «Показать» issues exactly one summary request carrying both selected dates. RED authenticity — before implementation the handler called `refresh()` (state+events) and never the summary endpoint, so `tests/test_681_682_road_crossing_period.py::RoadCrossingPeriodTests.test_period_query_issues_one_summary_request_with_both_dates` failed (phase RED: 13 failed / 1 passed; the 1 passing is the documented non-RED invariant `test_date_inputs_default_to_same_non_empty_date` — date inputs non-empty and equal).
- AC-002: the period response renders into the KPIs and the per-class table, and a subsequent 3-second state refresh does not overwrite it (`crossingStatsMode` guard), with a stale response never committing (`crossingStatsRequestSeq`).
- AC-003: an invalid range (from > to) renders an error row and issues no request; a summary failure renders an error row and keeps the previously shown numbers.
- AC-004: `#cxLast` shows the summary's `last_crossing_at` rendered in Asia/Vladivostok (never the browser clock), and «Нет данных» when the summary has none (null/invalid).
- AC-005: `#cxLiveBtn` returns to live mode and the next state render restores the state counts; the existing road twin (`tests/test_frontend_contract.py`, 18 road tests) and the full battery stay green.

## Runtime feedback
- Issue #681: on the pre-change tree `cxShowBtn.onclick` called `refresh()` — the date inputs were dead UI and the panel always showed live state counts; the period request path did not exist.
- Issue #682: the deleted line `cxLast.textContent=new Date().toLocaleTimeString()` displayed the browser clock — on any operator machine outside Vladivostok the shown time was wrong by the timezone offset, and it advanced on every render regardless of whether any crossing had occurred.
- Two emergent fixes during implementation: (a) `cxFrom`/`cxTo` were initially missing from the element bindings — a ReferenceError caught by the test harness before any commit; (b) the timestamp must render with an explicit `timeZone:"Asia/Vladivostok"` — without it the node process's local timezone shifts the displayed time (the #682 bug class re-entering through the fix itself).
