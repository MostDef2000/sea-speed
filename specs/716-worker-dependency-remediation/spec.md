# Spec: Ubuntu worker dependency remediation — clear the four advisory-bearing transitive pins in the runtime lockfile

- Feature: 716-worker-dependency-remediation
- Issue: #716
- Status: Implemented
- Owner outcome: the Ubuntu worker runtime resolves to a hash-locked graph with 0 known vulnerabilities and still installs and imports exactly as before.

## Product outcome
Issue #716 closes a vulnerability-coverage gap in the Ubuntu worker runtime. The dependency audit that gates the repository reads only the direct manifests — `deploy/worker/ubuntu/requirements-runtime.txt` for the worker and `api/requirements-api.txt` for the API — so it reported "No known vulnerabilities found" while the graph actually installed into the worker venv carried advisories. The new #686 full-lockfile audit read the resolved worker lockfile instead and found 58 advisories across four transitive packages the direct manifest never names: pillow 12.3.0 (42 advisories, fixed in 13.0.0), filelock 4.0.12 (13, fixed in 4.2.1), certifi 2026.7.22 (2, fixed in 2026.10.18) and setuptools 84.0.0 (1, fixed in 84.1.0). The change upgrades exactly those four pins in `deploy/worker/ubuntu/requirements-runtime.lock.txt` — to certifi 2026.11.20, filelock 4.3.0, pillow 13.0.0 and setuptools 84.2.1 — leaves the other 53 pins at their exact previous versions, and updates `resolved_lock.sha256` in `deploy/worker/ubuntu/runtime-lock.json` to the new lockfile digest so the runtime's hash cross-check accepts the new bytes. No worker source, deploy script, workflow or manifest changes. The product outcome is a worker runtime whose resolved graph has 0 known advisories, installable through the same two-phase hash-locked path, with a rollback that is one merge-commit revert and one redeploy.

## User scenarios

### Scenario 1 — The worker runtime resolves with no known advisories
Given the Ubuntu worker deploy installs `requirements-runtime.lock.txt` through `prepare-runtime.sh`, when the new lockfile is installed, then certifi 2026.11.20, filelock 4.3.0, pillow 13.0.0 and setuptools 84.2.1 replace the four advisory-bearing versions, the other 53 pins keep their exact versions, and a full-lockfile audit reports 0 vulnerabilities for the 57-dependency worker graph.

### Scenario 2 — The hash-lock cross-check accepts the new bytes
Given `prepare-runtime.sh` validates `runtime-lock.json` against the lockfile before any mutation, when the lockfile is regenerated, then `resolved_lock.sha256` equals the SHA-256 of the new lockfile bytes, the `# sea-speed-runtime-lock-v1` marker is the first line, and the PyTorch cu130 pins (torch 2.13.0+cu130, torchvision 0.28.0+cu130) keep their exact versions and verified artifact digests.

### Scenario 3 — A maintainer reviews the diff
Given a maintainer reads the two changed files, when they compare the new lockfile with the previous revision, then exactly four `name==version` pins differ (each with its regenerated hash lines), every other pin line is unchanged, the header is the canonical resolver command with no reference to the temporary constraints file, and `runtime-lock.json` differs only in `resolved_lock.sha256`.

### Scenario 4 — Rollback
Given the new graph must be undone, when the orchestrator reverts the merge commit and redeploys the previous worker lockfile, then the worker installs its previous pinned graph again through the same two-phase hash-locked path and the deploy transaction activates the previous runtime id.

## Requirements
1. Surgical upgrade: regenerate `deploy/worker/ubuntu/requirements-runtime.lock.txt` with `uv pip compile --generate-hashes --index-url https://download.pytorch.org/whl/cu130 --extra-index-url https://pypi.org/simple --index-strategy unsafe-best-match --python-version 3.14`, pinning all 53 non-target packages to their existing versions through a temporary constraints file and passing `--upgrade-package` for exactly the four targets.
2. Exactly four version changes: certifi 2026.7.22 to 2026.11.20, filelock 4.0.12 to 4.3.0, pillow 12.3.0 to 13.0.0, setuptools 84.0.0 to 84.2.1. Every new version is at or above its advisory fix version (2026.10.18, 4.2.1, 13.0.0, 84.1.0 respectively).
3. All 53 other pins unchanged: the torch/torchvision cu130 closure and every other transitive pin keep their exact previous versions and hash lines; no package may be added, removed, upgraded or downgraded beyond the four targets.
4. Self-contained artifact: strip every `-c runtime-constraints.txt` reference emitted into the generated `# via` comments and restore the header to the canonical resolver command, so the committed file references only files that exist in the repository and keeps the `# sea-speed-runtime-lock-v1` marker first.
5. Digest pair: update `deploy/worker/ubuntu/runtime-lock.json` `resolved_lock.sha256` to `e20d765263221f52ac4b7cb55a522d627eec122b300514e5012b37b300aebbca`, the SHA-256 of the new lockfile bytes; no other field in that file changes.
6. Provenance preserved: `runtime-lock.json` `pytorch.index_url`, `index_provenance`, `pypi_index_url`, `packages` and `artifact_sha256` stay byte-identical, and the new lockfile still carries the pinned torch/torchvision artifact hashes those fields name.
7. Bounded surface: only those two files change. No `worker/**` source, test, deploy script, workflow, lock input, manifest or API lockfile is edited.
8. Verification: `tests/test_ubuntu_worker_runtime_hash_lock.py` passes (24 tests), the full Python battery stays green (1439 tests OK, skipped=2), the repo/contracts/quality/workflow/token validators and ruff PASS, and a full-lockfile audit reports 0 vulnerabilities for the worker graph (57 dependencies) and the API contour (23 dependencies).

## Runtime feedback
- Coverage-gap class: the gate read the direct manifest (7 pins) while the runtime installs the resolved lockfile (57 pins), so every advisory below the top level was invisible to the audit. The finding was real, not a false positive: the four packages were versions with published advisories actually shipped into the worker venv.
- Source of the finding: Security gates run `44975403396`, artifact `pip-audit-reports-4aa072f20ca90928b74aea0a83a81b7075d2add8.zip` — the #686 full-lockfile audit that motivated issue #716; the advisory split was pillow 42, filelock 13, certifi 2, setuptools 1.
- Implementation feedback: a full re-resolution would have upgraded unrelated transitives, so the regeneration pinned the 53 non-target packages through a temporary constraints file and used `--upgrade-package` for the four targets only. The constraints path leaked into generated `# via` comments; those references were stripped and the header was restored to the canonical command, so the committed artifact is self-contained and has the exact shape a resolver-workflow regeneration produces.
- Verification feedback: this sandbox cannot reach pip-audit's default PyPI advisory service, so the local full-lockfile check used `pip-audit --disable-pip --vulnerability-service osv` (worker: 57 dependencies, 0 vulnerabilities; API: 23, 0). The CI audit that produced the original 58 uses the default service and re-verifies on the exact head, so the local run is corroboration rather than the authoritative gate.
- Risk feedback: pillow 12.3.0 to 13.0.0 is a major bump on the worker image-processing path. The available regression evidence is the full battery, the exact-head CI re-run and the deploy transaction's post-activation identity checks; that combination is why the risk is recorded explicitly in plan.md instead of being treated as routine maintenance.
